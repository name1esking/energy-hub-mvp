
# Energy Hub MVP — Scope and Requirements

**Версия:** 0.1 Draft  
**Дата:** 7 ноября 2026  
**Статус:** Требует согласования  
**Основа:** `DATA_MODEL.md` из PR #4, документация PR #1–#3.

## 1. Назначение документа

Документ определяет предполагаемый объём MVP Energy Hub, обязательные требования, KPI-кандидаты и вопросы, которые необходимо согласовать с Tech Lead и другими ответственными участниками.

Документ не утверждает неподтверждённые бизнес-правила, права пользователей или операции с энергетическим оборудованием.

## 2. Статус требований

В документе используются три категории:

- **Обязательное требование** — функциональность, необходимая для MVP, в пределах уже подтверждённой модели и текущего прототипа.
- **KPI-кандидат** — показатель, предлагаемый для отображения, но требующий подтверждения формулы, единиц измерения и источника данных.
- **Вопрос на согласование** — решение, которое нельзя принимать без подтверждения ответственного участника.

## 3. Обязательные требования MVP

### 3.1. Dashboard

MVP должен предусматривать:
- обзор основных энергетических показателей;
- отображение доступных данных по объектам;
- графическое представление энергетических показателей;
- отображение событий и предупреждений;
- отображение состояния качества данных;
- отображение доступных энергетических сервисов, если соответствующие данные предоставлены.

### 3.2. Управление объектами и оборудованием

Предусмотреть:
- просмотр списка энергетических объектов;
- просмотр оборудования, связанного с объектом;
- отображение доступных характеристик оборудования;
- отображение текущего статуса оборудования;
- просмотр истории измерений и событий, если данные доступны.

Создание, изменение и удаление объектов или оборудования требуют отдельного согласования.

### 3.3. Energy Monitoring

Предусмотреть:
- отображение измерений мощности и энергии;
- отображение генерации и потребления;
- отображение данных по импорту и экспорту из сети при наличии источника;
- отображение уровня заряда батареи при наличии соответствующего оборудования;
- графики изменения показателей во времени.

Необходимо корректно отображать отсутствующие, устаревшие и оценочные данные. Отсутствующее значение нельзя автоматически трактовать как нулевое.

### 3.4. Events & Alerts

Предусмотреть:
- список событий;
- отображение типа, времени и связанного объекта;
- визуальное выделение предупреждений;
- просмотр деталей события.

Подтверждение, закрытие и изменение статуса событий требуют согласования.

### 3.5. Data Quality

Предусмотреть:
- отображение доступности измерений;
- обозначение пропущенных данных;
- обозначение устаревших данных;
- отображение подозрительных или некорректных значений, если это поддерживается согласованной моделью.

Окончательный перечень статусов качества данных должен быть согласован с Tech Lead.

### 3.6. Energy Services

Предусмотреть отображение доступной информации об энергетических сервисах.

Подключение, отключение, настройка и управление сервисами не входят в подтверждённые обязательные операции MVP до согласования.

## 4. Роли пользователей

В документации и прототипе используются четыре роли:

| Роль | Предполагаемая область интерфейса |
|---|---|
| `platform_admin` | Общий обзор платформы |
| `portfolio_owner` | Обзор портфеля объектов |
| `hub_operator` | Операционная информация по объектам и оборудованию |
| `building_owner` | Информация по отдельному зданию или объекту |

Это описание предполагаемой области интерфейса, а не утверждённая матрица бизнес-прав.

Для каждой роли необходимо согласовать:
- доступные объекты;
- доступные разделы;
- доступные KPI;
- разрешённые действия;
- ограничения на изменение данных.

Наличие переключателя ролей в UI не является подтверждением серверной авторизации.

## 5. KPI-кандидаты

Следующие показатели обнаружены в материалах PR #1 и предлагаются для дальнейшего согласования.

### 5.1. Базовые измерения

| Показатель | Предварительный идентификатор | Единица |
|---|---|---|
| Мощность потребления | `consumption_power` | kW |
| Мощность генерации | `generation_power` | kW |
| Энергия потребления | `consumption_energy` | kWh |
| Энергия генерации | `generation_energy` | kWh |
| Экспорт в сеть | `grid_export_energy` | kWh |
| Уровень заряда батареи | `battery_soc` | % |
| Ограничение мощности | `power_limit` | Требует уточнения |

Идентификаторы предварительные и не являются утверждённым общим контрактом.

### 5.2. Производные KPI-кандидаты

| KPI | Предлагаемое назначение | Что требуется согласовать |
|---|---|---|
| Data completeness | Полнота поступивших измерений | Формула и период расчёта |
| Data quality score | Общая оценка качества данных | Веса и правила расчёта |
| Grid import | Расчётный импорт энергии из сети | Формула и доступные источники |
| Solar self-consumption | Собственное потребление солнечной генерации | Формула и границы системы |
| Solar self-consumption % | Доля собственного потребления | Формула и обработка отсутствующих данных |
| Limit excess | Превышение установленного лимита | Порог и правила определения |

Производные KPI не должны считаться окончательно утверждёнными до согласования формул и источников данных.

## 6. Предлагаемые разделы интерфейса

На основании UI PR #3 предлагается следующая структура:

1. Dashboard — общая сводка.
2. Portfolio — список и обзор объектов.
3. Energy Monitoring — измерения и графики.
4. Assets — оборудование и его состояние.
5. Events & Alerts — события и предупреждения.
6. Data Quality — состояние и полнота данных.
7. Energy Services — информация о сервисах.

Окончательная навигация и состав разделов требуют согласования с UI/UX.

## 7. Действия, требующие согласования

Следующие операции нельзя считать разрешёнными для конкретной роли без подтверждения Tech Lead:

- `acknowledge_events` — подтверждение событий;
- `change_limits` — изменение лимитов;
- `manage_operating_modes` — управление режимами работы;
- `manage_maintenance` — управление обслуживанием;
- `add_prepared_object` — добавление подготовленного объекта;
- `add_asset` — добавление оборудования;
- `manage_service_catalog` — управление каталогом сервисов;
- `connect_services` — подключение сервисов;
- `disconnect_services` — отключение сервисов;
- `configure_service` — настройка сервисов.

Перечень является списком вопросов для согласования, а не утверждённой спецификацией разрешений.

## 9. Критерии приёмки MVP

| ID | Критерий |
|---|---|
| AC-01 | Dashboard отображает доступные основные показатели |
| AC-02 | Пользователь может просматривать доступные энергетические объекты |
| AC-03 | Пользователь может просматривать связанное оборудование |
| AC-04 | Измерения отображаются с корректными единицами |
| AC-05 | Доступные измерения могут отображаться на графике |
| AC-06 | Отсутствующие значения не подменяются нулями |
| AC-07 | События отображаются с датой и связанным объектом |
| AC-08 | Предупреждения визуально отличаются от обычных событий |
| AC-09 | Состояние качества данных можно просмотреть |
| AC-10 | KPI используют согласованные формулы и единицы |
| AC-11 | Интерфейс не показывает неподтверждённые действия как разрешённые |
| AC-12 | Документация отражает согласованные роли и ограничения |

Критерии, зависящие от неподтверждённых решений, считаются предварительными до согласования.

## 10. Что не входит в подтверждённый объём MVP

До отдельного согласования за пределами подтверждённого объёма остаются:

- промышленный backend;
- серверное хранение данных;
- подключение реальных источников телеметрии;
- серверная авторизация;
- автоматическое управление энергетическим оборудованием;
- автоматическое изменение лимитов;
- полноценный workflow обслуживания;
- управление подключением и отключением сервисов;
- финансовые расчёты и биллинг;
- неподтверждённые интеграции со сторонними системами.
