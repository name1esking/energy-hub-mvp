# Соответствие сценариев модели данных

Документ сверяет пользовательские и операционные сценарии с `DATA_MODEL.md` версии 0.1.

## 1. Сущности, которые уже есть в модели

| Сущность | Что можно использовать в сценариях | Ограничение |
|---|---|---|
| `Portfolio` | Группа энергетических объектов | Не описан явный список `siteIds` или обратная связь `Site` → `Portfolio` |
| `Site` | Название, местоположение, тип, оборудование, показатели, события, сервисы | Не описаны поля и связь с `Portfolio` в виде точной схемы |
| `Asset` | `id`, `name`, `type`, `siteId`, `status`, параметры | Нет истории обслуживания, команд управления и даты обслуживания |
| `Measurement` | `id`, `siteId`, `metric`, `value`, `unit`, `timestamp`, `quality` | Нет правила диапазонов, частоты обновления и источника измерения |
| `Event` | `id`, `siteId`, `title`, `description`, `severity`, `status`, `timestamp` | Не определены значения `status`, исполнитель, комментарии, история обработки |
| `ServiceInstance` | Факт подключённого сервиса подразумевается | Нет полей, статусов, параметров и процесса подключения |
| `User` | Пользователь и роль подразумеваются | Нет полей роли, связи с `Portfolio`/`Site`, состояния пользователя |
| `Dashboard` | Представление по объекту, роли, оборудованию, измерениям и сервисам | Не описаны структура, виджеты, фильтры и правила сравнения |

## 2. Покрытие основных сценариев

| Сценарий | Сущности | Статус |
|---|---|---|
| Открыть список объектов портфеля | `Portfolio`, `Site`, `User` | Частично: не хватает связи пользователя с портфелем |
| Открыть карточку объекта | `Site`, `Dashboard` | Поддерживается на уровне концепции |
| Просмотреть оборудование | `Site`, `Asset` | Поддерживается |
| Просмотреть показатели | `Measurement` | Поддерживается |
| Показать отсутствующие / устаревшие данные | `Measurement.quality`, `Measurement.value` | Поддерживается |
| Просмотреть события | `Event` | Поддерживается для отображения |
| Изменить статус события | `Event.status` | Не определены допустимые статусы и переходы |
| Изменить лимит мощности | `Measurement` (метрика лимита) | Недостаточно: измерение не равно команде изменения настройки |
| Подключить / отключить сервис | `ServiceInstance` | Недостаточно: структура и жизненный цикл не определены |
| Провести обслуживание оборудования | `Asset`, `Event` | Недостаточно: нет записи обслуживания и истории работ |
| Сравнить объекты | `Portfolio`, `Site`, `Measurement`, `Dashboard` | Частично: нет правил временного интервала и сопоставимости |
| Показать блоки Dashboard условно | `Asset`, `Measurement`, `ServiceInstance` | Поддерживается как правило построения Dashboard |

## 3. Что требуется добавить или уточнить

### Приоритет 1 — доступ пользователей к объектам
В `User` или связанной структуре определить:
- идентификатор пользователя;
- значение роли из четырёх существующих ролей;
- доступные `portfolioIds` и/или `siteIds`;
- правило наследования доступа от `Portfolio` к входящим `Site`.

Не создавать новую роль. Названия сущностей не менять.

### Приоритет 2 — `ServiceInstance`
Согласовать поля, например:
- `id`, `siteId`, тип сервиса (`Peak Shaving` или `PV Self-Consumption`);
- `status` и допустимые значения;
- параметры сервиса;
- дата подключения / отключения;
- кто и каким действием изменяет состояние.

Это предлагаемые поля, а не уже утверждённая схема.

### Приоритет 3 — лимиты мощности
Разделить:
- измеренное значение фактической мощности;
- настроенное значение лимита;
- историю изменения лимита;
- автора, время и результат изменения;
- правило подтверждения и применения.

Сейчас `Measurement` содержит метрику «Лимит мощности», но это само по себе не описывает редактирование настройки.

### Приоритет 4 — обработка `Event`
Определить:
- допустимые значения `Event.status`;
- переходы между статусами;
- какие роли могут выполнять переход;
- нужны ли исполнитель, комментарий и история изменений.

### Приоритет 5 — обслуживание `Asset`
Если в MVP требуется сценарий обслуживания, определить минимальную структуру записи обслуживания:
- связанный `assetId`;
- тип и описание работ;
- плановая дата и фактическая дата;
- исполнитель;
- статус работ;
- результат.

Это предложение по расширению модели, не существующая сущность текущей версии.

### Приоритет 6 — сравнение и Dashboard
Уточнить:
- временные интервалы сравнения;
- поведение при разных единицах или отсутствующих измерениях;
- структуру `Dashboard` и правила скрытия блоков;
- различие подключённого сервиса и доступных для него демонстрационных показателей.

## 4. Вывод

Просмотр объектов, оборудования, показателей, качества данных, событий и подключённых сервисов можно описывать на основе текущей модели. Сценарии изменения лимитов, обработки событий, подключения сервисов и обслуживания оборудования следует считать требованиями к согласованию, а не подтверждёнными возможностями текущей схемы.
