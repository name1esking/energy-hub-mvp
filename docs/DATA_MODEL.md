
# ENERGY HUB — DATA MODEL

Версия: 0.1
Статус: Draft — предварительная версия
Ответственный: Tech Lead

## 1. Назначение документа

Этот документ определяет единую структуру данных приложения Energy Hub.

Все участники команды должны использовать согласованные форматы данных.

Цель — обеспечить совместимость интерфейса, демонстрационных данных, пользовательских ролей и энергетических сервисов.

Проект представляет собой MVP-прототип.

На первом этапе используются демонстрационные данные без промышленного backend.

## 2. Основные сущности

В системе используются следующие сущности:

- Portfolio — группа энергетических объектов.
- Site — отдельный энергетический объект.
- Asset — оборудование объекта.
- Measurement — измерение энергетического показателя.
- Event — событие или проблема.
- ServiceInstance — подключённый энергетический сервис.
- User — пользователь системы.
- Dashboard — представление показателей объекта.

## 3. Структура объектов

Portfolio объединяет несколько объектов Site.

Каждый Site содержит:
- уникальный идентификатор;
- название;
- адрес или условное местоположение;
- тип объекта;
- список оборудования;
- энергетические показатели;
- события;
- подключённые сервисы.

Пример:

Portfolio
  ├── Site 1 — Завод
  │     ├── Solar Panels
  │     ├── Battery
  │     ├── Inverter
  │     └── Meter
  │
  └── Site 2 — Офис
        ├── Solar Panels
        ├── Battery
        └── Meter

## 4. Оборудование (Asset)

Типы оборудования:

- solar_panel — солнечные панели;
- battery — аккумуляторная система;
- inverter — инвертор;
- meter — счётчик;
- charger — зарядная станция;
- load — потребитель энергии.

Каждое оборудование должно иметь:

- id;
- name;
- type;
- siteId;
- status;
- параметры оборудования.

Возможные статусы:

- online;
- offline;
- warning;
- error.

## 5. Энергетические показатели (Measurement)

Система должна поддерживать следующие показатели:

| Показатель | Единица |
|---|---|
| Потребляемая мощность | кВт |
| Генерируемая мощность | кВт |
| Энергия потребления | кВт·ч |
| Выработанная энергия | кВт·ч |
| Отдача энергии в сеть | кВт·ч |
| Уровень заряда батареи | % |
| Лимит мощности | кВт |

Каждое измерение должно содержать:

- id;
- siteId;
- metric;
- value;
- unit;
- timestamp;
- quality.

Если значение отсутствует, используем null, а не 0.

## 6. Качество данных

Для измерений необходимо предусмотреть:

- complete — данные получены;
- missing — данные отсутствуют;
- stale — данные устарели;
- estimated — данные расчётные;
- simulated — демонстрационные данные.

Приложение должно уметь отображать проблемы качества данных.

## 7. События (Event)

События описывают проблемы и изменения на объекте.

Примеры:

- превышение лимита мощности;
- отключение оборудования;
- потеря показаний счётчика;
- низкий заряд батареи;
- восстановление оборудования.

Каждое событие содержит:

- id;
- siteId;
- title;
- description;
- severity;
- status;
- timestamp.

Уровни важности:

- info;
- warning;
- critical.

## 8. Пользовательские роли

В системе предусмотрены четыре роли:

1. platform_admin — администратор платформы.
2. portfolio_owner — владелец портфеля.
3. hub_operator — оператор энергохаба.
4. building_owner — собственник здания.

Каждая роль имеет собственные права доступа.

Подробная матрица прав будет согласована с участником №4.

## 9. Энергетические сервисы

В MVP предусмотрены два основных сервиса.

### Peak Shaving

Ограничение пикового потребления мощности.

Основные параметры:
- максимальный лимит мощности;
- фактическая мощность;
- превышение лимита;
- участвующее оборудование.

### PV Self-Consumption

Повышение собственного потребления солнечной энергии.

Основные параметры:
- солнечная генерация;
- потребление объекта;
- энергия, использованная на месте;
- энергия, отправленная в сеть;
- доля собственного потребления.

Подробная спецификация будет согласована с участником №5.

## 10. Автоматическое построение Dashboard

Dashboard должен формироваться на основе:

- выбранного объекта;
- доступной пользователю роли;
- имеющегося оборудования;
- доступных измерений;
- подключённых сервисов.

Если на объекте нет батареи, соответствующий блок не должен отображаться как действующее оборудование.

Если сервис не подключён, его показатели не должны выдаваться за реальные.

## 11. Правила интеграции

Все участники используют единые идентификаторы сущностей.

Основные правила:

1. Не создавать дублирующие структуры данных.
2. Не менять названия общих полей без согласования.
3. Использовать TypeScript.
4. Разделять демонстрационные данные и бизнес-логику.
5. Указывать единицы измерения.
6. Не заменять отсутствующие данные нулями.
7. Передавать изменения через Pull Request.
