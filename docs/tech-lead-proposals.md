# Предложения Tech Lead к DATA_MODEL.md v0.1 (не внедрены в общий контракт)

`DATA_MODEL.md` v0.1 — Draft. Этот список не изменяет общую модель и не утверждает неописанные в ней поля.

1. **Согласовать машинные значения `Measurement.metric`.** В документе даны русские названия семи показателей, не их API-коды. В демо временно: `consumption_power`, `generation_power`, `consumption_energy`, `generation_energy`, `grid_export_energy`, `battery_soc`, `power_limit`. Без единого enum графики и сервисы будут по-разному называть показатели.
2. **Уточнить поля и связи Portfolio/Site.** Демо использует `Portfolio {id,name}`, `Site {id,name,location,type,portfolioId}` и условные `type=industrial|office`. Не определены точные имена поля местоположения, справочник типов объектов и способ связи с портфелем. Нужно зафиксировать для общего UI.
3. **Утвердить схему `Asset.parameters`.** Демо использует объект `parameters`, ключи `panelCount`, `panelPowerKw`, `peakPowerKw`, `capacityKwh`, `ratedPowerKw`, `measures`, `socPercent`, и др. Нужны типизированные параметры по `Asset.type`, единицы и правила для составных объектов (панель/массив панелей).
4. **Определить допустимые `Event.status` и связь с оборудованием.** Демо предварительно принимает `open|resolved`. Желательны опциональные `assetId`, `resolvedAt` и `eventType`, чтобы связывать событие с конкретным инвертором и жизненным циклом, не парся `description`.
5. **Уточнить интервал измерения.** Демо считает `timestamp` началом часа, а энергию измеренной за час. Предложение: `intervalMinutes` или `periodStart/periodEnd`, плюс явная политика UTC/часовых поясов. Иначе легко ошибочно смешать мощность с энергией.
6. **Согласовать качество и источник данных.** Сейчас `simulated` и `complete` находятся в одном enum, хотя симулированный ряд тоже бывает полным. Возможны отдельные `source: 'simulation'|'meter'` и `quality` как валидность, или единое правило приоритетов. Для `stale` полезно поле времени получения (`receivedAt`).
7. **Рассмотреть невалидные показания.** `quality='invalid'` пока **не разрешён**. Предлагается либо согласовать новое значение, либо отдельные поля проверки `validationErrors`; иначе некорректные данные приходится изолировать вне рабочего набора.
8. **Дополнить метрики импорта из сети.** `grid_import_energy` в `кВт·ч` нужен для независимой верификации баланса и тарификации. Сейчас в документации указан лишь экспорт, а импорт в демо **расчётный**, не фактическое показание счётчика.
9. **Для динамических батарей согласовать метрики заряда/разряда.** Возможные `battery_charge_energy` и `battery_discharge_energy`, оба в `кВт·ч`, либо привязка к Asset по `assetId`. До согласования батареи в демо простаивают, иначе невозможно честно подтвердить энергобаланс по существующим метрикам.
10. **Согласовать поля `ServiceInstance` и правила подключения сервисов** с участником №5: `siteId`, идентификатор сервиса, статус подключения и параметры. Демо не маркирует Peak Shaving и PV Self-Consumption как активные: есть только базовые данные для их будущих расчётов.
11. **Формулу качества данных** считать предложением UI: полнота, вес `stale` и `estimated`, исключение обнаруженных ошибочных показаний из расчётов требуют командного решения. Сейчас индекс — самостоятельный расчёт, не поле общей модели.

**Нельзя объединять предложенные изменения с общими TypeScript-типами без подтверждения Tech Lead.** После согласования обеспечить совместимость с участниками UI, QA и Services.
